Payment audit report - non-executed remediation plan

Detailed Change Plan

Sequenced plan for turning the payment flow into a production-grade implementation. This file is intentionally a plan only; no implementation has been performed.

Summary Issues Register Change Plan Test Matrix Optimizations

Success Criteria

Payment correctness
Credits and subscriptions are granted only after provider-confirmed payment that matches server-side amount, currency, user, product, and idempotency state.
Security boundary
Clients can view billing state but cannot mutate billing records, grant credits, spoof users, or select trusted payment attributes.
Release readiness
Web, Android, Supabase, Razorpay, and Google Play policy flows are tested with repeatable automated checks and release gates.

Target Payment Architecture

Authenticated user Client sends bearer token and product ID only.
Server intent Server resolves price, currency, credits, plan, offer, and creates pending row.
Provider checkout Razorpay/Play Billing receives trusted server-created order or purchase product.
Verify and webhook Server verifies raw provider signals and stores idempotent event rows.
Ledger grant Transactional RPC grants entitlement once and creates audit trail.
Phase 0
Freeze and rotate

Stop the bleeding before larger refactors

  • Rotate committed Razorpay test secret and webhook secret.
  • Remove hardcoded secrets from scripts/docs and replace with placeholders.
  • Add secret scanning to CI.
  • Disable or hide Android Razorpay digital checkout for Google Play builds until policy path is decided.
  • Add environment preflight checks that fail startup/build when payment secrets or public Razorpay key are missing.
Gate: secret scanner passes, old webhook secret rejected, release build cannot produce undefined Razorpay key, and Android Play build has no non-compliant digital checkout.
Phase 1
Auth boundary

Require identity before any payment or credit action

  • Require Supabase bearer token on create-order, create-subscription, verify-payment, cancel-subscription, ai-proxy, and ai-stream.
  • Derive user_id from verified token. Remove body-supplied user identity as an authority.
  • Reject missing auth with 401 and mismatched user IDs with 403.
  • Fail closed if SUPABASE_SERVICE_ROLE_KEY is not configured for privileged server routes.
Gate: route tests prove unauthenticated and mismatched-user requests cannot create orders, verify payments, cancel subscriptions, use credits, or mutate usage rows.
Phase 2
Server-authoritative catalog

Remove client control over trusted payment facts

  • For credit packs, accept only pack_id. Fetch active pack price, currency, and credits server-side.
  • For subscriptions, accept only internal plan ID and billing cycle. Fetch Razorpay plan ID, offer ID, price, and credits server-side.
  • Create a payment_intents or equivalent table that stores user, product, amount, currency, provider order/subscription ID, status, and expiry.
  • Store Razorpay notes that match server intent, but treat notes as audit support, not the source of truth.
Gate: client tampering with amount, currency, plan ID, pack ID, offer ID, or user ID cannot change what the server creates or grants.
Phase 3
Verification and ledger

Grant exactly once, based on provider-confirmed facts

  • Use Razorpay signature verification with timing-safe comparison for checkout returns.
  • Fetch Razorpay order/payment/subscription from provider during verification when needed to confirm amount, currency, capture/payment status, and linked order/subscription.
  • Replace client-provided plan grant inputs with server-side pending intent lookup.
  • Create a durable billing ledger: intents, provider events, credit grants, refunds, subscription state changes, and reconciliation status.
  • Use unique constraints for provider payment ID, provider event ID, and credit grant idempotency key.
Gate: duplicate verification and duplicate webhook delivery cannot double-grant; underpaid and mismatched-provider payments are rejected.
Phase 4
Database hardening

Make billing writes server-only

  • Drop broad FOR ALL RLS policies on billing tables.
  • Add user SELECT policies for own billing rows and optional admin SELECT/MANAGE policies.
  • Move credit grants and consumption into SECURITY DEFINER RPCs with fixed search_path, explicit validation, and narrow grants.
  • Add constraints for non-negative credits, known plan IDs, valid status values, and no duplicate active subscription rows.
  • Audit all client fallback paths that currently insert/update subscriptions or credits directly.
Gate: Supabase tests prove authenticated client sessions cannot insert/update/delete billing tables directly, while server APIs still pass.
Phase 5
Webhook rebuild

Make provider callbacks reliable and replay-safe

  • Configure the webhook route to read raw request body before parsing.
  • Verify Razorpay signature from raw body and X-Razorpay-Signature.
  • Insert webhook delivery row first using provider event ID as a unique key.
  • Handle subscription activated, charged, completed, cancelled, halted, paused, and resumed events with explicit state transitions.
  • Return non-2xx on retryable internal errors. Return 2xx only after durable handling or known duplicate acknowledgement.
Gate: duplicate, out-of-order, invalid-signature, and DB-failure webhook tests pass.
Phase 6
Android payment path

Choose and implement the distribution-safe Android flow

  • If shipping through Google Play, implement Play Billing products for subscriptions and credits, or a documented eligible alternative billing/user choice flow.
  • Add backend purchase-token verification and subscription status sync for Play purchases.
  • Keep Razorpay checkout available only for web or allowed non-Play channels, controlled by platform/build flags.
  • Add Android emulator/device tests for purchase entry points and entitlement sync.
Gate: purchase flow passes on Android device/emulator and policy checklist is complete before Google Play release.
Phase 7
Regression suite

Make payment correctness enforceable

  • Add route tests for auth, tampering, idempotency, provider mismatch, and cancellation behavior.
  • Add Supabase/RPC tests for RLS and transactional credit grants/consumption.
  • Add webhook fixture tests based on Razorpay test payloads and signatures.
  • Add CI jobs: unit tests, TypeScript, lint, Vite build, Android assemble, Android lint, secret scan, and env validation.
  • Add release smoke checks for Razorpay test mode or Play test purchase flow.
Gate: all payment-specific tests and release checks pass in CI before launch candidate tagging.
Phase 8
Operations

Prepare for production support and reconciliation

  • Add structured logs with correlation IDs for intent ID, provider order ID, subscription ID, payment ID, and webhook event ID.
  • Add dashboards for payment success rate, webhook failures, duplicate deliveries, credit grants, and refund/cancel events.
  • Add daily reconciliation between Razorpay/Play and local billing ledger.
  • Create support tools for searching payments, replaying safe webhook events, and correcting entitlements with audit trails.
Gate: support can answer "who paid, what was granted, why, and when" from internal records without querying raw logs.
