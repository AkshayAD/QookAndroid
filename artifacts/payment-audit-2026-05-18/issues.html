P0 - Production Blockers

ID Issue Evidence Impact Required Change Acceptance Test
P0-01 Android digital goods are sold through Razorpay Checkout JS without Google Play Billing implementation. services/razorpayService.ts:168 loads checkout from checkout.razorpay.com.
android/app/build.gradle has no BillingClient dependency or user choice billing implementation. 		Google Play distribution can be rejected or suspended if digital subscriptions/credits are sold outside allowed Play Billing or eligible alternative billing flows. Decide distribution model. For Google Play: implement Play Billing for subscriptions/consumables or an eligible user choice billing flow with Billing Library support, reporting, purchase verification, and acknowledgement. For non-Play distribution: keep Razorpay but gate Android Play builds away from Razorpay digital checkout. Internal Android build passes a purchase flow using BillingClient or documented user choice billing. Play Console policy review checklist is completed before release.
P0-02 Credit pack amount tampering is possible because server trusts client amount and pack ID. api/create-order.ts:9 accepts amount_inr and pack_id from client.
api/create-order.ts:30 sends that amount to Razorpay.
api/verify-payment.ts:62 passes client plan_id to the DB RPC. 		A caller can request a low amount order while passing a high-value pack ID. If paid, HMAC verification succeeds and the server can grant credits for the high-value pack. Make backend authoritative. Client sends only pack_id. Server fetches active pack price/credits from Supabase, creates a pending payment row, stores Razorpay order ID, amount, currency, pack ID, and user ID, then verifies payment against the stored pending row and Razorpay order/payment status before granting credits. Tamper test: create a request where client claims pack_id=mega with a lower amount. API must ignore client amount or reject. Verify endpoint must not grant credits unless order amount, currency, user, and pack match server-side state.
P0-03 Subscription plan escalation is possible because server trusts client Razorpay plan and internal plan mapping. api/create-subscription.ts:11 accepts Razorpay plan_id and internal_plan_id from client.
api/create-subscription.ts:68 uses client plan_id for the Razorpay subscription.
api/verify-payment.ts:62 grants internal plan from request body. 		A caller can create/pay for a cheaper Razorpay plan while asking the app to grant a higher internal plan until corrected later, if ever. Client sends only internal plan ID and billing cycle. Server resolves Razorpay plan ID and any offer ID from trusted DB config. Store pending subscription intent. Verify and webhook handlers must resolve internal plan from stored server intent or provider plan details, never from client body. Tamper test: pay for the cheapest subscription but submit plan_id=family_pro in verification. API must reject and no paid entitlement should be granted.
P0-04 Payment routes do not require valid authentication; AI routes trust request body userId. api/create-order.ts:17 and api/create-subscription.ts:30 compare user IDs only when auth exists.
api/verify-payment.ts:21 requires payment fields but not auth.
api/ai-proxy.ts:83 and api/ai-stream.ts:353 accept userId from body. 		Unauthenticated callers can create payment objects, verify against arbitrary user IDs, or target another user's AI credits and usage rows if they know or guess identifiers. Every sensitive API route must require Supabase bearer token verification. Derive user_id from token, not request body. Reject missing token with 401 and mismatched user IDs with 403. AI routes must use authenticated user ID for credit queries and deduction. API tests cover missing token, invalid token, and token/body mismatch for create order, create subscription, verify payment, cancel subscription, AI proxy, and AI stream.
P0-05 Billing RLS policies allow client-side mutation of subscription and credit tables. supabase/migrations/20260111_subscription_system.sql:244 creates Users manage own subscription for all operations.
supabase/migrations/20260111_subscription_system.sql:245 creates Users manage own credits for all operations.
supabase/migrations/20260111_subscription_system.sql:247 creates Users manage own purchases for all operations. 		With broad RLS, authenticated clients can potentially insert/update their own credits, subscriptions, purchases, and rate limits, bypassing payment rules. Drop broad billing write policies. Keep SELECT policies for user-visible rows. Route writes through server-only APIs and locked-down SECURITY DEFINER RPCs. Grant execution only to trusted roles where appropriate. Add constraints to prevent negative balances and invalid plan states. Client anon/auth session attempts to insert/update user_credits, user_subscriptions, and credit_purchases must fail. Server payment RPC tests still pass through service role.
P0-06 Razorpay webhook handling is not production safe. api/razorpay-webhook.ts:52 reconstructs body with JSON.stringify(req.body) when raw string is not present.
api/razorpay-webhook.ts:117 returns success after handling.
api/razorpay-webhook.ts:122 returns HTTP 200 even when processing throws.
api/razorpay-webhook.ts:222 updates credits without event-level idempotency. 		Signature verification can fail if raw payload changes. Provider retries can be suppressed by HTTP 200 on internal failure. Duplicate events or replayed webhook calls can grant duplicate credits. Configure raw body capture for the webhook route. Verify X-Razorpay-Signature against raw bytes/string. Add a webhook event table keyed by Razorpay event ID. Return non-2xx on retryable processing failures. Deduplicate credit grants by payment/invoice/subscription cycle. Webhook tests cover invalid signature, raw body validation, duplicate event, replayed recurring charge, and simulated DB failure returning retryable 5xx.
P0-07 Payment secrets are committed in repository files. scripts/setup-razorpay.js:4 contains a Razorpay test key ID.
scripts/setup-razorpay.js:5 contains a Razorpay test secret.
DEPLOYMENT_STATUS.md:71 contains an actual-looking webhook secret. 		Exposed secrets can enable webhook spoofing in any environment using that secret and create confusion between test and production credentials. Rotate exposed Razorpay test secret and webhook secret. Remove secrets from files and history where required. Replace with placeholders. Add secret scanning to CI. Make setup scripts read from environment variables only. Secret scanner passes. Old webhook secret no longer accepted in Razorpay dashboard or deployed app. Repository has no payment secrets beyond documented placeholders.

P1 - High-Risk Gaps

ID Issue Evidence Required Change
P1-01 Service role key fallback can fail open into anon behavior. api/verify-payment.ts:53 and api/ai-proxy.ts:91 use SUPABASE_SERVICE_ROLE_KEY || VITE_SUPABASE_ANON_KEY. Billing and AI credit write routes must fail closed if service role is missing. Never use anon fallback for privileged operations.
P1-02 Local release assets can be built with undefined Razorpay key. Local Vite/Android assets contained key:void 0 when VITE_RAZORPAY_KEY_ID was absent. Add build-time environment validation for required frontend and backend variables. CI must fail before packaging if payment env is incomplete.
P1-03 Cancellation can remove paid access immediately despite user-facing cycle-end expectation. api/cancel-subscription.ts:86 sets status cancelled. services/subscriptionService.ts:905 also writes cancelled locally. Represent cancellation as cancel_at_period_end or equivalent. Keep entitlement active until renews_at/current_period_end. Separate billing cancellation state from entitlement state.
P1-04 Credit deduction has race-condition risk. api/ai-proxy.ts:300, api/ai-proxy.ts:320, and api/ai-stream.ts:440 update credits after reading balances. Move credit consumption into a transactional DB RPC with row locks, idempotency keys, and negative-balance prevention.
P1-05 Payment-specific tests are missing. Existing test suite passed, but no tests cover payment tampering, webhook retries, RLS billing mutation, auth rejection, or Android purchase flow. Add route, RPC, and webhook tests before remediation is considered complete. Use Razorpay test mode fixtures for integration tests.
P1-06 Pricing sources and components can diverge. components/PricingContent.tsx and components/PricingPage.tsx both implement pricing displays. Docs and migrations show mixed price fields. Use one pricing component and one server-side pricing source. Keep docs, DB rows, Razorpay plans, and UI in a reconciled release checklist.
P1-07 No complete billing ledger for audit, refund, and support workflows. verify_razorpay_payment writes billing_payment_events, but create/verify/webhook paths do not consistently store provider status, order fetch result, capture state, amount, currency, invoice, refund, and event payload. Create a normalized billing ledger: payment intents, provider orders, subscription events, credit grants, refunds, webhook deliveries, and reconciliation state.
P1-08 Rate limits and quota checks are partly client-side or bypassable. Client services call rate-limit helpers, while server AI routes focus on credit checks and trust body user ID. Enforce rate limits and abuse controls server-side using authenticated user ID and IP/device context. Return structured quota errors.

ID Issue Recommended Improvement
P2-01 CORS is broad on sensitive API routes. Restrict allowed origins for browser clients and keep strict bearer-token auth. Avoid * with credential semantics.
P2-02 Payment UI can render an empty plan surface when Supabase env/config is missing. Add explicit production-safe error states and telemetry for missing plan/pack config.

P2-06 Payment script uses hardcoded test credentials. Refactor setup utilities to read credentials from environment variables and print safe diagnostics only.
P2-07 TypeScript strict check is currently red. Fix existing test type errors so CI can reliably block regressions before payment changes ship.
