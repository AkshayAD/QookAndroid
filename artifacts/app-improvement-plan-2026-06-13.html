Qook — App Improvement & Payment Hardening Plan

Audit date 2026-06-13 · Production = QookCommander af321c3 (www.qook.in) · App lineage = QookAndroid 16fde7a · v1.0.12 (versionCode 13)
Method: 4 parallel deep-audit agents (payment backend ×high-reasoning, payment frontend, Android/Capacitor, general sweep) + every P0 hand-verified against the actual production files and the live site.

Executive Scorecard

🔴 Account deletion APIUnauthenticated on production — anyone with a user ID can delete that account. Verified live.
🔴 Razorpay backend (prod)Not production-safe: client controls the charged amount & granted plan; webhook grants are not idempotent.
🔴 Android monetizationApp users cannot purchase at all (checkout hard-blocked on native), and the "web checkout" steer risks Play policy.
🟠 Payment page UXNo double-click guard, no modal-dismiss recovery, plan badge stale after purchase, fabricated "50% OFF" strikethroughs.
🟠 Pricing truthDocs, UI, and DB disagree on pack contents, referral reward, weekly bonus, and credit expiry.
🟠 AI cost controlSeveral Gemini-spending endpoints have no credit cost or per-user quota — your API bill is exposed.
🟡 Frontend/UX coreSolid flows; gaps in failure recovery (SSE parsing, bootstrap cache), modal accessibility, context re-renders.
🟢 Android platform basicstargetSdk 36, allowBackup=false, no cleartext, compiled Tailwind bundle — store-compliant foundation.
Bottom line: the payment plumbing (signatures, JWT auth, RLS lockdown from the 2026-06-12 rollout) is in place, but the payment economics are not enforced server-side: the client tells the server what to charge and what to grant. Combined with the unauthenticated delete-account endpoint, production needs an emergency batch before any growth push. The QookAndroid lineage already contains most of the hardened payment code (20260518_payment_hardening.sql, intent-based verification) — the core fix is porting it to production, not inventing it.

🚨 Emergency Fixes — production, this week

E1 · Unauthenticated account deletion (LIVE vulnerability)

P0 api/delete-account.ts (prod) has no auth check whatsoever: it reads userId from the request body, uses the service-role key, and even sets Access-Control-Allow-Origin: *. It cancels the victim's Razorpay subscription, soft-deletes their data, and deletes the auth user. Verified live: an anonymous POST reaches the handler ({"error":"Missing userId"}).

Fix (small, ~20 lines):
  • Add authenticateSupabaseUser(req.headers.authorization) and require authUserId === userId (same pattern already used in create-order.ts:15-21).
  • Drop the wildcard CORS header (use the ALLOWED_ORIGINS approach from lib/serverApi.ts).
  • Note: the QookAndroid lineage version is already JWT-guarded — this was the one endpoint the 2026-06-12 port missed.
Validate: 401 unauthenticated, 403 cross-user, 200 self (staging user) → browser-smoke preview → promote → re-probe prod.

E2 · Client controls charged amount and granted plan

P0 Two halves of the same hole, independently confirmed:

  • api/create-order.ts:9,30 — charges client-sent amount_inr (and currency); the server never looks up the pack price.
  • api/verify-payment.ts:64-73 — after signature check, grants whatever client-sent plan_id/type says via verify_razorpay_payment RPC; the RPC (20260328_unified_credit_billing.sql:892+) never compares the paid amount to the pack/plan price.
  • Same pattern on subscriptions: create-subscription.ts trusts client plan_id/total_count/offer_id.

Exploit: pay ₹19 for the Starter pack, call verify with plan_id = mega → 50 credits for ₹19. Signature verification does not prevent this — the signature only proves a payment happened.

Fix — server-side price binding with payment intents (the Android lineage already implements this pattern):
  1. Client sends only pack_id (or internal plan id). Server looks up the active price, hardcodes INR, creates the Razorpay order.
  2. Persist an intent row (order_id → user_id, pack_id, amount, status=pending) — the billing_payment_intents table from 20260518_payment_hardening.sql (file exists in QookAndroid lineage, not yet applied to live DB — needs the live-vs-repo audit already tracked in RECONCILIATION_TRIAGE).
  3. verify-payment loads the intent, fetches the payment from the Razorpay API, asserts captured + amount + currency + order match, then grants from the intent, never from client fields.

E3 · Webhook can double-grant credits; fails open

  • P0 razorpay-webhook.ts:181 — subscription.charged grants credits on every delivery; Razorpay retries ⇒ repeated grants. The dedupe table billing_webhook_events already exists in the schema but is never used. Client-side verify-payment grant can also overlap the webhook grant for the same charge.
  • P1 razorpay-webhook.ts:54 — signature verification is skipped if RAZORPAY_WEBHOOK_SECRET is unset → env misconfiguration silently makes billing mutations unauthenticated. Fail closed.
  • P1 razorpay-webhook.ts:118 — processing errors still return HTTP 200, so Razorpay never retries; paid users can silently miss credits. Return 5xx on transient failure (after signature check), or persist the event and process idempotently.
  • P2 razorpay-webhook.ts:52 — HMAC computed over JSON.stringify(req.body) (re-serialized) instead of raw body bytes — valid signatures can fail on serialization differences.
Fix: dedupe by Razorpay event_id + payment_id into billing_webhook_events before granting; one idempotent ledger shared by verify-payment and webhook (unique constraint on payment_id); raw-body HMAC; fail-closed secret handling.

7 · Decisions only you can make

D1 — Android monetization. Options: (a) Google Play Billing — policy-correct, unblocks in-app revenue, costs 15% fee + integration work (recommended if the app is a growth channel); (b) consumption-only app — remove all upgrade/buy CTAs and "go to website" wording from the Android build (cheap, policy-safe, but app users can never convert in-app). Current state (blocked checkout + web steer text) is the worst of both.
D2 — Paid credit expiry. UI says "never expire", DB says 180 days. Honoring "never expire" is the trust-preserving choice (set validity_days null for paid packs); if you want expiry, the UI/terms must say so explicitly before more purchases happen.
D3 — Cancellation semantics. Today: immediate local "cancelled" + message claiming access until renewal. Decide: cancel-at-period-end (industry default, recommended) vs immediate + proration. The E-batch state machine work implements whichever you pick.
D4 — Referral reward (+2 vs +3) and weekly free bonus (1 vs 3) — pick numbers; everything else is mechanical alignment.
