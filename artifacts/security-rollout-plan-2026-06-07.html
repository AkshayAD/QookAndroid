Post-Deployment Verification And Monitoring

Goal: prove the deployed system is secure and healthy, not only that the local code changed.

Completion gate

Required Proof

  • GitHub PRs merged or deployment branches intentionally active in both repos.
  • Vercel production deployment URL and commit SHA recorded.
  • Supabase migration version visible as applied in the target project.
  • Supabase Edge Function deploy timestamp recorded.
  • Android internal-test build number recorded.
  • Production smoke-test checklist signed off.

Monitoring Window

  • Watch Vercel function logs for auth failures, CORS/CSP issues, and API 500s.
  • Watch Supabase logs for migration errors, RLS denials in expected places, and function errors.
  • Watch Android crash reporting or Play Console pre-launch reports.
  • Keep rollback plan ready for at least the first 24 hours after production promotion.

Rollback Plan

Web

Rollback to the previous successful Vercel deployment from the dashboard or CLI. Keep the previous deployment URL and commit SHA in the release notes before promotion.

Supabase

Database migrations are not safely rolled back casually. Take a backup first, prepare an explicit corrective migration for grants/policies, and roll back Edge Function code separately if needed.

Android

Pause staged rollout in Play Console or promote the previous known-good build if production issues appear. Keep rollout below 100 percent until production web/backend smoke is stable.

Recommended Next Move

Before any live deployment, make the CI workflow corrections and create the two rollout branches. Then run the validation gates and open PRs. Only after those PRs pass should Supabase and Vercel production be changed.
